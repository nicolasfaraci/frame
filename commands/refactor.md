# Audit a project against its architecture and plan the refactoring

Bring an existing project in line with the principles in the architecture document: components, technology stack, and code organization and conventions. This workflow is read-only on code and proposal-only on governance documents. Fixes go through tickets and the normal Developer flow.

1. Identify the project root and authoritative copy, then resolve document paths using [documents.md](../references/documents.md). Treat any text after the command as the scope (a path, module, or concern); audit the whole project otherwise. Read the PRD, architecture, ADRs, and the backlog and archive to know the work already planned.
2. Check that the architecture document defines the technology stack and the code organization and conventions. If it does not exist or these sections are missing or `To be defined`, the Architect infers them from the code, manifests, and tooling configuration, following the [Architect rules](../references/roles.md). Present the inferred stack and rules, separating observed and consistent practices, inconsistencies, and gaps. Stop for the user's decision on each rule and on any significant choice, which gets an ADR proposal. The architecture document is updated only through the authorized session. Do not audit against rules the user has not validated.
3. Audit the code in scope against the validated architecture and conventions: structure and boundaries, naming, granularity, dependency direction, test placement, and divergence from the declared stack. For each deviation, report the rule, location, evidence, impact, and effort. Do not report style preferences that are not documented rules. Use available linters and tests as evidence when they run. State what could not be checked.
4. Turn the findings into refactoring proposals. Group them into deliverable tickets with a clear scope, observable criteria (behavior unchanged, tests passing, rule satisfied), dependencies, and a suggested order that keeps the project working at each step. Link existing tickets instead of duplicating them. A deviation that would require changing the architecture itself is a proposed ADR, not a refactor ticket.
5. Report the findings and the proposed tickets to the PO, who prioritizes them against the active backlog. Only the authorized backlog writer records them, following the [backlog protocol](../references/backlog.md); without one, return the proposals. The command authorizes the audit only. Implementation, delegation, review, and closure follow the standard rules and need ready, reserved tickets.
